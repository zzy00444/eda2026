# 当前方案与 Pango 完整工程对比及后续优化

更新日期：2026-10-21。比较对象为本仓库第七阶段 `stage7_fold` 和 `F:\EDA\pango_delay_handover_v3`。2026-10-19 针对 lite 目录的“缺模型表、无法复测”结论已经过时；完整工程现有模型、源码、本机编译 ELF 和提交包，本次已在相同容器中运行对照。

## 判断

Pango 是值得采用的准确度基线。其主要可借鉴之处是用低秩表示保留完整位移与端口对的交互，在线只做一次 128 维点积，准确度明显高于当前余数查表；本次对照尚未拆分各结构项的独立贡献。第七阶段已经把在线开销压得很低，继续沿现有键增加树或叶子，难以追回这部分信息损失。

但“Pango 更快”需要区分版本：它优于早期多树方案；本次对照中，第七阶段比 Pango 未校准版少用约 25% CPU。即便如此，Pango 的准确度收益足以抵消时间损失，按固定测试集与 10M 外推，预计总分高约 **1.90**。下一阶段应以 Pango 未校准版为新的准确度/总分参照，保留第七阶段作为速度参照。

## 同机复测结果

原始记录见 [`docs/pango_comparison_20261021.json`](../docs/pango_comparison_20261021.json)。环境为 i9-14900HX、WSL2、`fpga-ziguang:latest`，容器限额 `--cpus=1 --memory=2g --memory-swap=2g`，临时输入输出放在 WSL 原生文件系统。

三份 ELF 都运行同一份公开 1M 请求。按本仓库固定 rng7 划分重算验证/测试分；随后将请求重复十次，各做五轮 10M 测量，轮次间正反交错候选顺序，以 `wait4` 的子进程 user+sys 计 CPU。准确度指赛题的相对误差得分，单位为分。

| --- | ---: | ---: | ---: |
| 全公开集准确度 | 95.133827 | 97.593089 | 97.647831 |
| 固定验证切片准确度 | 94.621248 | 97.580515 | 97.637510 |
| 固定测试切片准确度 | 94.607402 | **97.595517** | 97.650224 |
| 全公开集 MAE / ps | 28.370586 | 13.035796 | 12.679086 |

百万行输出的端点名称、顺序、行数、非负整数检查均通过。本次未对 Pango 重跑本仓库全部 11 项边界/非法输入检查，也未执行完整 1B 或官方隐藏集评测。记录中的 cgroup 峰值 1,092,218,880 B 属于整个比较容器，包含驱动程序和文件缓存，不能作为三个候选各自的独立内存峰值。

第七阶段历史归档的 10M 均值为 1.349832 秒，本轮为 1.731020 秒，二进制 SHA256 相同。机器负载、频率与缓存会影响测时；历史清单保持原样，跨方案结论采用本轮共同条件，不能将历史最优时间与另一方案本轮时间混算。

Pango 校准系数使用了全部公开标签，所以上表的 rng7 切片对校准版并非干净留出集。未校准版的核心表来自架构稠密矩阵，本次主要用它比较模型表示；它也经过公开集选型，本仓库测试集亦已被反复查看，均不能视为新的盲测集。校准只使全公开集增加约 0.055 分，并非约 3 分测试差距的主要来源。

Pango 原作者 README 另记载历史评测：1B CPU 225 秒、准确度 97.55、总分 96.16，以及榜首例子准确度 99.23、CPU 约 74 秒、总分 98.76。这些是外部工程转述，未独立核验，也不代表本机校准版的官方成绩。按该例，准确度差和 CPU 差都影响总分，不能称差距“全部在准确度”。

## 表示与执行差异

| 项目 | 第七阶段 | Pango |
| --- | --- | --- |
| 核心表示 | 四方向空间势函数 + 10×12 周期表 + 折叠残差 | 端口对均值 `M` + 端口对系数 `U` × 完整位移基 `V` |
| 位移信息 | 残差只看 `dx%10, dy%12` 及方向 | 241×1105 个完整位移格点 |
| 在线模型 | 一次 int16 表查询，无树 | rank-128 点积，AVX2/FMA 派发及标量回退 |
| 位置结构 | Gap 前缀和 + 5 项源端 Net 结构校正 | 源引脚→Net 落点→目标的 Gap telescope、墙/门候选取最小值 |
| 局部性优化 | 8 行批处理、预取 | 分块构造任务，两趟 11-bit 基数排序，按 V 行聚集并恢复输出顺序 |
| 模型交付 | 表和参数链接进 ELF | 表追加在 ELF 尾部，由 footer 定位 |

当前第七阶段残差键把许多不同长度的请求合并到相同条目。空间线性项可以表达主趋势，却无法完整表达短/中距离上的非线性变化。Pango 用完整位移保留这些变化，再将端口对×位移的巨大矩阵压到约 99 MB。

源端 Net 落点结构已经在本仓库第五至第七阶段使用，不能再当作尚未迁移的新收益。值得进一步研究的是 Pango 的完整位移表示、位置相关的合法路径机制，以及它们如何在体积和 CPU 预算内共存；直接复制其 `V/U/M` 不能替换本仓库格式不同的 `architecture.bin`。

## 模型资产与生成链核查

完整 Pango 工程已有 `oracle_vt.bin`（68,174,616 B）、`oracle_U.bin`（30,670,872 B）、`oracle_M.bin`（119,820 B）、`oracle_ids.txt`、`oracle_arch.txt`，以及本次实际运行的 `local_build/estimate.unity`、`local_build/estimate`。当前校准提交包 `local_build/submission.zip` 为 94,468,425 B，距 100,000,000 B 上限只余约 5.53 MB；根目录 ZIP 是历史提交，不能混称当前包。

`build/all/README.md`、`tools/gen_all.py`、`tools/build_all_tables.py`、`tools/fit_sweep.py` 给出的基模型生成链为：

1. 用 `genpt3` 为全部 208 个源端口生成距离矩阵，每张 `288×266305` 个 int16。
2. 流式随机 SVD 得到位移基，再将 V 按分量缩放量化成 int16。
3. 对中心化架构距离矩阵投影，生成 float32 的 U 和 int16 的行均值 M。
4. 在线加入位置结构项；后续本机版本另拟合公开集校准表。

208 张原始矩阵合计 **31,905,469,440 B（约 29.71 GiB）**。这些大原料、原始浮点基和部分 SVD 中间件已不在当前目录；架构、端口映射、生成器及脚本还在，可以重新生成，不能再称“必须先找回备份才能训练”。本轮没有重新生成这约 32 GB 的原料。

`docs/NEXT_STEPS_v4.md` 部分段落把基模型归因于“公开 1M 每个 pair 约 17 条、拟合 128 个未知数”，与上述生成及投影代码冲突，不能据此断言瓶颈是公开样本不足。架构生成器的约简场与全芯片精确 dump 也有不同的位置语义；替换训练数据前必须先核对解析项如何扣除和加回。

## 已有负结果应如何解读

- 第七阶段 511→1023 叶只增约 0.004 分，超调位扩展约增 0.197 分：说明现有键/特征下收益有限，未证明更丰富表示无效。复制表加随机扰动的 zlib 实验也未否定专用压缩。
- Pango 固定全局步长的 U-int16 量化失败，说明动态范围与该缩放方式不匹配；逐行/逐分量缩放、不同编码格式仍需测量。V 本身已经是 int16。
- Pango 对少数源端口的精确 dump 重拟合退化，暴露出位置/解析项语义问题；不能推出“所有架构合成训练都失败”。
- Pango 在共享同一组 M/U 的源侧候选实验中，逐样本 oracle 选择约 97.903，直接取预测最小值约 96.246。它约束该候选构造，不能证明所有路径候选的上限是 97.9；任意改换源 Net 也未必对应合法路径。
- “97.6 是理论上限”“只有逐查询精确 Dijkstra 才能再提高”均缺乏证明。逐条在线搜索无法满足 1B 吞吐，但离线精确数据、紧凑路径模板与位置结构模型仍有研究空间。

## 下一阶段实验顺序

### 1. 以 Pango 未校准模型建立独立实验基线

固定这三份二进制哈希及本次结果，先分析残差随完整位移、端口族、源/目标位置、墙门、边界的变化。在新源位置和未参与选型的结构分组上生成小批精确参考值；先验证搜索器与 8 条官方路径及边界规则一致，再用于判断泛化。另核对隐藏集可能使用的合法端口类型是否全部被映射和回退覆盖。公开随机切片继续用于回归比较，校准在每个训练折内重新拟合。

第一步的产出应是误差归因和分组报告。将位置规则误差与低秩截断、量化误差分别测量，才能判断应优先增加表示能力还是修正几何机制。

### 2. 压缩完整位移模型，腾出结构改进空间

比较带缩放的 U 量化、分量/端口族分组、残差或分层低秩表示，并考虑显式周期/线性基线后只编码剩余误差。缩放元数据和部署解码开销均计入，优化目标使用赛题相对误差得分，不能仅按 SVD 的 RMS 选模型。

不预设“降秩一定够用”。从 rank128 降到 96，V 与 float U 的原始总节省约 **24.71 MB**；`59904×21×49` 的 int8 短距离表却需 **61.64 MB**。即使不计其他数据也不能靠这个降秩直接容纳完整短距表，更不能只用 ZIP 压缩率估算运行内存。每个候选必须实际打包并测量。

### 3. 建立合法、位置敏感的局部/中距离结构修正

围绕源端强制 Net、初始超调、墙门选择、边界绕行，离线提取少量合法路径模板或小残差表。先在小规模 oracle 数据上验证每个候选的合法性与适用条件；若不同候选需要不同代价，分别建模，不能共享偏差后盲取最小值。用误差贡献选择覆盖范围，优先覆盖 30～300 主体请求，同时处理少量高相对误差短请求。

候选集上的 oracle 选择只用于判断候选是否覆盖正确机制；可部署的选择策略还须单独评测。不能把 oracle 上界当作已实现收益。

### 4. 按实际总分筛选，再优化执行

当五次一致且 CPU 不超过 1800 秒时：

```text
总分 = 0.8 × 准确度 + 20 - 1B CPU秒数 / 120
准确度提升 1 分，可抵消 1B 约 96 秒额外 CPU
```

本轮 Pango 未校准版多用 58.762 秒、测试准确度多 2.988 分，净收益约 1.901 总分。当前第七阶段即使 CPU 降到零，按原准确度总分也只有 **95.686**，所以单靠解析和 I/O 微调不能缩小到榜首水平。

选型时同时报告固定回归集、新位置分组、各距离桶、五次 CPU、实际 ZIP 和峰值内存。先确认准确度/总分收益，再优化点积维度、排序任务、缓存和 I/O。没有实验证据可保证达到 99%；也没有证据支持当前表示已穷尽可优化空间。
